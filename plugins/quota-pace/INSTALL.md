# quota-pace: quota pace

**Source:** this folder is the single source of the plugin. Changes are made here only; they reach the machines with `git pull` + `install.sh`/`install.ps1` (in direct mode with `git pull` alone, see below).

## Target time

The first version forecast the weekly quota at the **moment of the reset**. This version forecasts at a **target moment N hours before the reset**: `target = reset − N hours`. The aim is to move at a pace that uses up the whole quota 5 hours before the reset.

- **Setting:** the `PACE_TARGET_HOURS` environment variable (hours, default `5`). Without the variable the `"target_hours"` field of `~/.claude/pace-plan.json` is read (safer when the environment variable does not reach the process that starts the status line). `0` behaves exactly like the original script (the N=0 output was verified to equal the old script's). The **upper limit** is 72 hours by default (it used to be 48); `"max_target_hours"` in `pace-plan.json` changes it, but no setting goes above 96 hours (4 days before the reset). `target_hours` and `max_target_hours` pass the same limit whether they come from the environment or the file.
- **Target percent (`target_percent`):** says **which percent you want to be at** at the target moment (`"target_percent"` in `~/.claude/pace-plan.json`, or the `PACE_TARGET_PERCENT` environment variable; default `100`, valid range 50-100). The modes (PLENTY/NORMAL/TIGHT) and the forecast aim at this percent: every percent threshold is scaled by `target_percent / 100` (for 90 the thresholds 80/85/95/100/105/110 become 72/76.5/85.5/90/94.5/99). `100` is the old behaviour. `need_rate` (the percent per hour needed to reach the target) also follows this percent. The old `"target"` field only affected `need_rate` (default 90, it never changed the modes); `target_percent` replaces it when given, otherwise `need_rate` still reads `target`. `target_percent` is added to `pace.json` and `pace-forecast.json`; `pace-hook.py` writes `goal 90%` in its line when the target percent is below 100.
- **Example: 90% on Friday 09:00.** With the reset on Sunday 21:00, Friday 09:00 = reset − 60 hours. `~/.claude/pace-plan.json`: `{"target_hours": 60, "target_percent": 90}` (other fields stay). Until Friday 09:00 the forecast picks the mode against 90% (TIGHT when the forecast is above 90%, PLENTY below 72%); after 09:00 it is PLENTY, since the leftover quota is lost at the reset. When the `--last-window` option of `install.sh` is on, the last window starts from the same `target_hours` value (60 hours = Friday 09:00): the last-window work then uses the leftover quota from Friday morning on.
- **The 95% hand-over rule does not depend on the target percent.** The rule asks for a hand-over when the weekly use reaches `>= 95%` before the target moment; that number is a fixed buffer below the hard limit, not a percent of the target. With a 100% target it hands over 5 points under the buffer; with a 90% target 5 points above the target (between 90% and 95% the `[Quota >= 90%]` message comes: keep working, finish and push). After the target moment (after Friday 09:00) the rule is off and the leftover quota is used. So reaching 95% before Friday morning with a 90% target is a real overrun and the hand-over is the right behaviour; no extra setting is needed.
- Median/P10/P90 are computed at the target moment. The "last 2 days" (the window where the P90 conditions apply) count against the target. `active_hours_left` is the active hours left until the target.
- `target_at` (the target time, epoch) and `target_hours` are added to `pace.json` and `pace-forecast.json`.
- **After the target has passed** (the last N hours): the mode is **PLENTY**, since the leftover quota is lost at the reset.
- **The mode comes from the weekly forecast only (decision 04.11.2026).** The 5-hour window is not part of the mode: when it fills, work only pauses until its reset and then continues where it stopped; it restricts no work. The status line (`5h 86% (1h23m)`) and `pace-hook.py` ("5-hour window 86% used, resets 23:40 (information only, restricts no work)") show it as information only; `five_hour_used` / `five_hour_resets_at` stay in `pace.json`. Everything that reads the mode (`cost_share.work_order()`, the last window, the triage owner lease) is therefore not affected by the 5-hour window. The earlier 5h ≥ 70%/80% rule was removed.
- Mode thresholds: PLENTY (median < 80% and P90 < 100%; kept up to median 85% / P90 105%), TIGHT (median > 100% or P90 > 110%), NORMAL in between. The P90 conditions only count in the last 2 days before the target.
- The `pace-hook.py` message shows the target as "Forecast at the target (Sat 24.10 21:00, reset -5h)"; once the target has passed it gives a separate sentence. `statusline.ps1` and `statusline.sh` keep their output format and only carry the `target_at` / `target_hours` fields into `pace.json`.
- **When the 5-hour window is not reported** (Claude Code sends no `five_hour` in `rate_limits`; per the docs each window may be missing on its own): `five_hour_used` in `pace.json` is `null` (not 0), the status line shows no `5h` segment, `pace-hook.py` writes no "5-hour window" sentence, and the 3rd column of `pace-history.csv` stays empty. When Claude Code reports the window again everything comes back by itself.

## Files

- `bin/pace_forecast.py`: the forecast (Python stdlib only). `--selftest` runs 16 checks (a-l the old behaviour with N=0, m and n new, o: 5h not reported, p: target percent and 60 hours). Tests: `tests/test_pace_target_percent.py`.
- `bin/pace-hook.py`: the `[Quota pace: MODE]` line in the session.
- `statusline.ps1` (Windows), `statusline.sh` (Linux, needs `jq`).
- `bin/statusline-local.ps1`: the wrapper. When `pythonw` is not on PATH it finds it under `%LOCALAPPDATA%\Programs\Python\Python3*\` and puts it on PATH (otherwise the forecast silently stops updating), then calls `statusline.ps1`. The paths are parameters (`-ClaudeDir`, `-StatusLine`, `-Extra`). `statusline.ps1` runs in the same process (no second `pwsh`). Put personal warnings not here but in the optional `~\.claude\bin\statusline-extra.ps1` (`param([string]$Line)`, returns the changed line); `install.ps1` never touches that file. **Line wrapping (0.3.3, margin measured in 0.3.4):** when all segments fit the terminal width the wrapper prints one line (the same bytes as before); otherwise it splits the line into pieces (` | ` and ` · ` are equal break points) and fills each row greedily with as many pieces as fit; a piece is never split, a row never starts or ends with a separator, the separator between pieces stays as it is (the cost segment spreads over two rows at its `· ` points when needed). Width order: `QUOTA_LINE_WIDTH` (manual) > `COLUMNS` (Claude Code passes it to the status line process) > 120. Margin `QUOTA_LINE_MARGIN` (default **4**, measured on the real screen, see below; each unit of `statusLine.padding` in `settings.json` adds 2). Wrapping runs after the `statusline-extra.ps1` output. The example `example/statusline-extra-two-line.ps1` is no longer needed (wrapping happens by itself); it stays for anyone who always wants the line split in two at the folder segment regardless of the width, and it keeps working (its output is wrapped by width too). Linux/macOS `statusline.sh` wraps with the same rule (`bin/line_wrap.py`, installed under `~/.claude/bin`; the same `QUOTA_LINE_WIDTH` / `QUOTA_LINE_MARGIN` settings): width order `QUOTA_LINE_WIDTH` > `COLUMNS` (Claude Code passes it; measured in the real process as `COLUMNS=236 LINES=62`, no `stty`/tty, `tput cols` mirrors COLUMNS) > `/dev/tty`; none of them = no wrapping (there is no 120 default as on Windows). On Windows the wrapping stays in PowerShell (so the wrapper does not depend on Python); `test_line_wrapping.py` checks that both implementations give the same output.

### Line wrapping: the measured margin (0.3.4)

In 0.3.3 the margin (10) was a guess. In 0.3.4 it was measured by running the real `claude` (2.1.310, Windows 11) in a ConPTY and reading its screen with a terminal emulator (pyte): `tests/test_real_screen.py` (with `QUOTA_UI_TEST=1`, skipped by default; its header says how to run it). Results:

- The status line process gets `COLUMNS` and `LINES` **equal** to the pty size (verified at 80/120/160/204/250 columns).
- Claude Code does **not wrap** a status line; it cuts what does not fit with `…`. There are 2 columns of indent on the left and 2 empty columns on the right: a line shows at most **columns - 4** cells (exactly 4 at 80, 120, 160, 204 and 250 columns, in both the full-screen and the classic view; found by binary search). `statusLine.padding` in `settings.json` is added on both sides (padding 2 -> margin 8, padding 5 -> margin 14). Hence the default margin **4**: a line that fits exactly stays one line.
- Resizing the window does **not by itself rerun** the status line command; it runs with the new `COLUMNS` at the next event (a new assistant message, `/compact`, a permission mode change and so on). Until then the old line shows cut to the new width with `…`. If you want, add `"refreshInterval": N` (seconds, at least 1) to `statusLine` in `settings.json`; every N seconds a `pwsh` starts, so do not use a small value.
- Notifications on the right: in the full-screen view they are on their own row and do not affect the status line. In the classic view the `◐ medium · /effort` notice moves to the next row when the line is full; the status line does not get shorter. Not verified for other notices (update, context warning).
- With the real wrapper at 204 columns: a 200-cell line stays one line, a 201-cell line becomes two (step 4 of the test prints the screens).

## Install

Requirements: Python 3 (on Windows also PowerShell). On Linux/macOS the status line also needs `jq`; `install.sh` stops with an error when jq is missing (macOS: `brew install jq`, Debian/Ubuntu: `sudo apt install jq`). Windows needs no jq.

- **Windows:** `pwsh -File <clone>/plugins/quota-pace/install.ps1` (works with PowerShell 5.1 too: `powershell -File ...`)
- **Linux/macOS:** `bash <clone>/plugins/quota-pace/install.sh`

One command gives the same full status line on every operating system: the main line, the agent rows (`subagentStatusLine`) and the cost segments (`cache`, `session ₺X (₺x)`, the last action `₺20 (₺0,33)`, `last 7m ₺A (₺a)` (this session + its agents, since the last prompt) · `last 24h ₺A (₺a) · 7d ₺B $C (₺b) · 30d ₺D (₺d) · ×N`). The same command updates (run `git pull` in the clone first).

The script finds Python and `pwsh` by itself. In the legacy copy mode (`--copy` / `-Copy`) it copies the files under `~/.claude` (an existing different file is kept as `*.backup-<date>`); it backs up `settings.json` and merges the `statusLine` and the `SessionStart`/`UserPromptSubmit` hook entries (touches nothing else, writes paths with forward slashes). At the end it runs the hook and the status line once as a check. The same command is used for updates; an existing pace-hook entry is not added a second time but replaced in place.

Options: Windows `-WhatIf` (show the changes without writing anything), `-Remove` (remove our files and entries), `-Free` (install without the cost segments). Linux/macOS `--whatif`, `--remove`, `--free`. `--share` / `-Share` joins the usage ranking (below). The `statusLine` and `subagentStatusLine` commands in `settings.json` use the absolute path of the Python 3 found (Windows has no `python3`); a `subagentStatusLine` that belongs to someone else is left alone. When `settings.json` is not valid JSON the script stops without writing anything.

### Running from the clone (the default; `-Direct` / `--direct` is accepted)

- **Windows:** `pwsh -File <clone>/plugins/quota-pace/install.ps1 -Direct`
- **Linux/macOS:** `bash <clone>/plugins/quota-pace/install.sh --direct`

In this mode no script is copied under `~/.claude`: the `statusLine`, `subagentStatusLine` and pace-hook entries in `settings.json`, the `cost` command (`~/.claude/bin/cost.cmd` / `~/.local/bin/cost`) and the daily cost job (Task Scheduler, systemd, launchd) run the files in the clone directly. The plugin folder has the same layout as `~/.claude` (status line scripts at the top, the others under `bin/`); the scripts find their siblings relative to their own location, so they give the same output in both modes. Runtime data (`pace.json`, `pace-history.csv`, `cost/`, the personal `statusline-extra.ps1`) stays under `~/.claude`. Copies left by an earlier install are removed. The mode, the clone path and the install options are written to `~/.claude/quota-pace.json`.

**Automatic update:** when `tools/rules_watch.py` (the session-start hook, installed as described in the [README](../../README.md#change-warnings)) sees this file, it fast-forwards the clone's current branch from its upstream at every session start (`git fetch` + `git merge --ff-only`; on a personal branch the changes on `main` still come with `git merge origin/main`). It silently skips when the working tree has uncommitted changes, HEAD is detached, the branch has no upstream or a fast-forward is not possible. When the pulled commits touch `plugins/quota-pace` or `plugins/crew-agents/tools`, the install's own self-check runs (`install_common.py <install options> --probe`: both hooks, `cost --help`, the status line with a sample input, the agent row; a few seconds). When the check fails or does not finish in 30 seconds, the clone goes back to the commit before the pull with `git reset --hard` (the tree was clean before the pull, so no local work is lost) and the session start shows a warning naming the broken commit. That commit is not retried while it stays at the tip of the upstream (the warning repeats at every start); a new commit on top makes it try again. The hook never blocks the session (exit code always 0). Without the `rules_watch.py` hook updates come with a manual `git pull`; no reinstall is needed.

**Pros / cons:** one source, no manual reinstall: a fix that lands on `main` (or your own branch) runs in the next session. On the other hand, the code of everyone with push access to the branch runs on your machine at the next session start without you looking at it (in copy mode you run the `install` command yourself). Every change you make in the clone (switching branches included) affects your status line and hook at once; a bug the self-check does not catch (for example one that only shows with real quota data) arrives without waiting for the next `install` run, unlike copy mode. With a release that changes `settings.json` entries (a new hook, for example) run the install command once more. It cannot be combined with `--free` (to turn the cost segments off, create the file `~/.claude/cost/off`). To go back to copy mode run the install with `-Copy` / `--copy` (the copies are put in place, `quota-pace.json` is deleted); `-Remove` / `--remove` removes either mode.

Optional: to change the target time set the `PACE_TARGET_HOURS` environment variable or write `{"target_hours": 4}` into `pace-plan.json` (see the Friday 09:00 and 90% example above). Then restart Claude Code.

### If it broke

When the hook blocks every prompt (for example `can't open file ...Usersuser.claudebinpace-hook.py`), open a normal PowerShell window outside Claude Code and run `install.ps1` again (Linux: `install.sh`). It repairs the broken entry in place and does not add a second one.

### Manual install (only when the script does not work)

Put the files where the script would copy them (the plugin's `bin/` folder → `~/.claude/bin/`; `statusline.ps1` → `~/.claude/`). Use **forward slashes only** in the `settings.json` commands; backslashes (`\`) are swallowed by Claude Code's bash and the hook blocks every prompt. The hook entry (change USER and the Python path to yours):

```json
{ "type": "command", "command": "C:/Users/USER/AppData/Local/Programs/Python/Python313/python.exe",
  "args": ["-I", "C:/Users/USER/.claude/bin/pace-hook.py"], "timeout": 10 }
```

`statusLine`: `{ "type": "command", "command": "pwsh -NoProfile -File C:/Users/USER/.claude/bin/statusline-local.ps1" }`.

## Cost statistics (in the default install)

The default `install.sh` / `install.ps1` also adds day/week/month/year and rolling 24h/7d/30d statistics of the Claude Code spend: the `cost` command, the record (every 2 hours at :23; Linux/systemd: a user timer; macOS: the launchd user agent `~/Library/LaunchAgents/com.agentcrewkit.cost-daily.plist`, every 2 hours at :23, loaded with `launchctl bootstrap gui/$UID`, the same file reloaded on a reinstall; Windows: the user-level Task Scheduler task `cost-daily`, no admin rights needed; on Linux without systemd the status line's background refresh writes the same daily record), the status line segments `cache NN%`, `session ₺X (₺x)`, the last action `₺20 (₺0,33)` (only the main session's own requests; agents in their own row; the parentheses always hold the real subscription cost, without a calibration the parentheses and `×N` are not shown), `last 24h ₺A (₺a) · 7d ₺B $C (₺b) · 30d ₺D (₺d) · ×N` (`×N`: how many times cheaper the subscription is than the API list price), `₺380 (₺6,33)` in the agent rows, and the local dashboard. The amounts are the **API list-price equivalent of the token usage, not a bill**; everything stays local and is sent nowhere. Who does not want them gives `--free` / `-Free`. Details: [COST.md](COST.md). `install.sh --remove` removes all of it (the recorded history stays).

## Joining the usage ranking (one command)

Joining the team's daily usage ranking (details: [README](../../README.md#usage-ranking-optional)) means adding `--share` to the install command. First the shared repo must be set (`CLAUDE_SHARED_REMOTE` or `~/.config/claude-shared/remote`: the clone address of the team's own repo; README, Configuration), `gh auth login` + `gh auth setup-git` must be done (write access to the shared repo is needed) and your name must be in `plugins/quota-pace/people.json` of the shared repo.

- **Linux / macOS:** `bash plugins/quota-pace/install.sh --share --plan 100`
- **Windows:** `pwsh -File plugins/quota-pace/install.ps1 -Share -Plan 100`
- `--plan` is `100` or `200` (the subscription, dollars/month). When your git name differs from the listed name add `--person "First Last"` (Windows `-Person "First Last"`); for example Gül, whose git name is `example-tester-1`: `--person "Gül Ersoy"`.

What the command does, in this order; when a step fails **nothing is installed**: (1) it compares the name with `people.json` (when it is invalid it lists the valid names) and checks the plan; (2) it builds and prints the row with `cost --share --dry` (writes it nowhere); (3) it pulls the shared repo into the job's own clone, checks that the name is in `people.json` on `main` and checks write access with `git push --dry-run` (without access it stops with the `gh auth login` / `gh auth setup-git` instructions, exit code 3); (4) it writes the files `~/.config/claude-shared/person` and `plan` (on Windows `%USERPROFILE%\.config\claude-shared\`, where `cost_share.py` reads them); (5) it installs the job with `--save --share` (Linux systemd timer, macOS launchd agent, Windows task; all every 2 hours at :23; an old `cost-daily.timer.d/*.conf` that only sets `OnCalendar` is backed up and removed). Each run commits only when the row or the ranking really changed. The first row is written at the next run, or at once with `cost --save --share`. The same command is for updates and can be run again (identical files pass as "same"). An install without `--share` still makes the daily job run only `--save`; when the previous install was sharing, the command says so with a warning. `--remove` removes the job, the `person`/`plan` files stay. `--whatif` checks the name/plan, writes nothing and does not go to the network. A bare `-WhatIf` / `--whatif` previews a bare run: it uses the saved options (`setup` in `~/.claude/quota-pace.json`) as they are.

## Last window (opt-in, `--last-window`)

In the last hours before YOUR weekly quota reset (the forecast's target window: reset minus `PACE_TARGET_HOURS`, default 5 h) all leftover quota is spent on pre-approved work that needs no human approval, so nothing is lost at the reset. Nothing runs unless you opt in.

- **Install:** `bash plugins/quota-pace/install.sh --last-window [--person "First Last"]` (Windows: `pwsh -File plugins/quota-pace/install.ps1 -LastWindow [-Person "First Last"]`). The options saved by the last install are kept: a re-run with only the new flag adds it and keeps the rest (for example `--last-window` after `--share --plan 100`); the installer rewrites the daily job each time. No switch drops one saved option; `--remove` removes the whole install. Needs `claude`, `gh` (logged in, push access to claude-shared), `tmux` on Linux/macOS (for the fallback session) and your name in `people.json`, like `--share`; the plan is not needed. Remove with `--remove` (the shared log stays).
- **What gets installed:** the `last-window` command, and a per-user timer that runs `last-window trigger --modes <modes>` every 5 minutes (`window` with `--last-window`, `resume` with `--resume-alarm`; Linux: systemd user timer `last-window.timer`; Windows: Task Scheduler task `last-window`, runs only while you are logged on (the Windows Terminal tab fallback is untested); macOS: command only). The timer costs nothing; the script acts only when `week_resets_at - PACE_TARGET_HOURS <= now < week_resets_at`, the weekly use is below 100 %, no assignment is running (lock) and the last start was 15 or more minutes ago.
- **What runs:** a normal, visible, interactive Claude Code session, never a headless `claude -p`. When the window opens (and at every tick inside it while no assignment is active) `last-window` ranks your **live terminal sessions** (`~/.claude/sessions/*.json`, entrypoint `cli`): highest model first (Opus, Sonnet, Fable, Haiku, by the ladder scores 58/54/49/40; the model is the last assistant message in the session's transcript), then the newer model version, then the **oldest-started** session. Headless runs (`entrypoint sdk-cli`), `last-window*` sessions, unnamed sessions, sessions whose name is shared by several live ones, and the names in `LAST_WINDOW_EXCLUDING` / `~/.claude/last-window/excluding.txt` (optional, one shell pattern per line, empty by default) are skipped. The chosen session receives the full brief (rendered to `~/.claude/last-window/runs/<ts>-brief.md`) as a cross-session message, sent by a one-shot headless Haiku relay (`ListAgents` + `SendMessage`, the same pattern as the other relays; a few cents). The message starts with `[last-window on <machine>]`. When the relay answers `HANDOFF`, the run stays with that session: a busy session shows the message only at the end of its current turn, so the wrapper keeps following it and never hands the same brief to a second session; only a session that sits idle for `LAST_WINDOW_ACK_SEC` (5 minutes) without the message ends the run (`handoff-unseen`, nobody else gets it). The next candidate (three at most) gets it only after a clear `MISSING` or a relay that could not run; a relay that times out (`LAST_WINDOW_ROLE_SEC`, 300 s) or answers neither word may have sent, so that run hands nothing out (`handoff-unknown`) and the next tick tries again. No candidate is tried and no fallback started once the reset is near (the last 10 minutes for a run that started before them). **Fallback:** with no reachable live session, `last-window` starts its own visible session `last-window-<person>`: interactive `claude` (bypassPermissions, `--name`, Remote Control on) in a detached tmux session of the same name on last-window's **own tmux server** (`tmux -L last-window`: it never joins or starts your default tmux server; under systemd that server lives in the unit's cgroup and ends with the run), brief as the first prompt; the first-run "trust this folder" dialog of your repos root is answered once by the wrapper (the folder the coordinator always ran in; dialog text checked on Claude Code 2.1.316). Nothing else on screen is ever answered: **the bypass-permissions warning must have been accepted once by you in an interactive session** (`claude --permission-mode bypassPermissions`, choose "Yes, I accept"); the wrapper never accepts it for you. The wrapper waits up to `LAST_WINDOW_RECORD_SEC` (120 s) for the started session to register itself; if it does not (a dialog it may not answer, a crash), the session's screen goes to `~/.claude/last-window/last-window.log`, the session is killed and the run is recorded as `error` (three such quick failures in a row back off for an hour). The wrapper stays in the foreground holding the lock, follows the session through its registry entry and transcript (status, turn count, items from the journal), ends the run at the reset (assigned session: a "reset reached" message, relayed again while the relay fails or while the session sits idle without it, at most `LAST_WINDOW_RESET_ATTEMPT` (3) relays, outcome in the log; the session is yours and is never killed; fallback session: `Escape`, `/exit`, then `kill-session`), when the weekly limit is used up, after `LAST_WINDOW_MAX_TURNS` (200) assistant turns (hand-off message first), when the session idles for 10 minutes after working (`LAST_WINDOW_IDLE_SEC`), or when it closes (an assigned session that gets a new session id after `/clear` is followed by its pid and name); with quota left the next tick assigns again. Quota readings come from `pace.json` (the status line of the working session keeps it fresh). Your normal settings must let the session use its tools (the fallback runs in bypassPermissions like your own sessions); the installer never changes permissions. `LAST_WINDOW_MODEL`, `LAST_WINDOW_ARGS` (extra `claude` args of the fallback), `LAST_WINDOW_RC=0` (no Remote Control), `LAST_WINDOW_MAX_TURNS` are copied (with `PATH`, `SSH_AUTH_SOCK`) from the installing shell into the systemd unit.
- **Watch it:** `last-window session` prints the live sessions, the ranking and who would get the assignment. While a run is active, `last-window status` ("This machine") names the session; the run row in `reports/last-window/` and `LOG.md` carries `session:<name>` at the start of its Items cell. An assigned session is simply a session you already have open (the message appears in it as `Message from @...`; the relay session that sent it has already exited, so replies to it fail by design). The fallback: `tmux -L last-window attach -t last-window-<person>` (detach with `Ctrl-b d`; a plain `tmux attach` looks at your own server and does not see it; Windows: the `last-window-<person>` Windows Terminal tab), it also shows in `ListAgents` / `claude agents`-style session lists as `last-window-<person>` and, with Remote Control, in the session list at claude.ai/code and in the Claude mobile app (Code tab; needs a claude.ai subscription login and Remote Control accepted once with `/remote-control`; checked 01.11.2026 on Claude Code 2.1.316: `claude <prompt> --name N --remote-control N` starts unattended and prints the session URL). For an assigned session Remote Control is whatever that session has (`/remote-control`, or `remoteControlAtStartup` in `~/.claude/settings.json`).
- **Test without a real run:** `last-window attempt --tmux --reset-sec 120` starts a throwaway `last-window-test` fallback session with a trivial prompt in a scratch state dir (own lock, log and journal, no gate, no shared-log row; it never touches a live session) and cuts it off at the simulated reset; `last-window attempt --send last-window-test-<x> --reset-sec 120` does the delivery to a throwaway live session of that name (names that do not start with `last-window-test` are refused).
- **Work order:** (a) issues labelled `ai-last-window` (created by `last-window label` in the repos listed in the config key `LAST_WINDOW_REPOS`, settings file `product-repos`); (b) board Status "AI queue" issues without `prod-approval-waiting`, dev-branch only, highest priority first, unassigned or yours (assigned to you when started); (c) the standing list: red or flaky tests/CI on dev, independent reviews of "In review" items (comment only), docs and test-scenario gaps, Dependabot on dev with green tests, read-only audits. Strong rungs, several items in parallel, hardest first, WIP pushed after every step, one Slack status line per item.
- **Never in this mode:** test/master/prod, deleting data or backups, customer machines, messages to people (only the Slack status lines), purchases, Vault/permission/firewall/network changes, product-behaviour decisions, shared lab VM image changes.
- **See and follow:** `last-window trigger --dry-run` prints the gate decision and the picks and starts nothing; `last-window choice` prints only the picks; `last-window status` prints the latest runs of everyone. Each run writes `~/.claude/last-window/<date>.md` locally and one row (written when it starts, replaced when it ends) to `reports/last-window/<person>.md`; `reports/last-window/LOG.md` lists all people, newest first (same ownership rules as the usage ranking: only your own file, name from `people.json`).
- **Stop it now:** `systemctl --user stop last-window.service` (Windows: end the task) stops the run (the wrapper ends a fallback session; an assigned session of yours simply keeps working until you tell it to stop); `systemctl --user disable --now last-window.timer` stops the timer.

### 5-hour resume alarm and burn mode

Both are modes of the same `last-window` command and timer (one gate, `decision(mode=...)` in `bin/last_window.py`), with the same journal, shared log and never-list.

- **Install the resume alarm:** Windows `pwsh -File plugins/quota-pace/install.ps1 -ResumeAlarm`, Linux `bash plugins/quota-pace/install.sh --resume-alarm` (same name/push checks as `--last-window`; remembered by a bare re-run; `--remove` removes it). With `--last-window` too the timer runs both (`trigger --modes window,resume`).
- **What the resume alarm does:** when the 5-hour window is used up (`pace.json` `five_hour_used` = 100, written by the status line) and its reset (`five_hour_resets_at`) has passed by 10 minutes, every live terminal session whose last transcript entry is still the 429 "You've hit your session limit" stop gets ONE relay: continue the work you were doing (git status, task list, agents' hand-offs, WIP), pick nothing new. Exactly one relay per stop: the reset time and each stop's uuid are recorded in `~/.claude/last-window/resume.json` before any relay (own file and lock `resume.lock`, so it also works while a last-window or burn-mode run holds the coordinator lock). When `pace.json` already shows a newer window (sessions that auto-continued wrote it), the stops are read from the transcripts. No new session is opened and no new item is picked. Claude Code's own `autoContinueAtUsageLimit` (on by default) resumes an open session at the reset; the alarm covers what it misses (Esc pressed, three automatic continuations used, sleep over 30 minutes). Without a usable `pace.json` the stops are read from the transcripts alone (reset = stop + 5 h at the latest, stops older than 12 h are left alone). Spend-limit and weekly-limit stops are never resumed.
- **Burn mode on/off (developers only):** `last-window burn --on`, `last-window burn --off`, `last-window burn` (state). The command reads your GitHub login (`gh api user`) and accepts only `role: developer` in `people.json`; testers and management are refused, and `--on` is refused inside a session last-window started (`LAST_WINDOW=1`) and while a last-window run is live. These are guards against accidents, not a security boundary (the files are local). The state (who, when, the weekly reset at activation) is in `~/.claude/last-window/burn.json`; the status line shows ` | BURN` while it is on.
- **What burn mode does:** outside the target window, each tick hands the last-window assignment (work order (a) `ai-last-window`, (b) "AI queue" not `prod-approval-waiting`, (c) the standing list; same never-list, one Slack status line per item, WIP pushed after every step) to your best live session or the visible fallback session. A full 5-hour window ends the run; after the reset the resume alarm wakes the other stopped sessions and burn mode assigns again. It stops when the weekly limit is used up, switches itself off at the weekly reset stored at activation, and a running assignment gets a stop message within seconds of `--off`. A run that found nothing to do holds the next start for 1 hour. Runs log as `burn/<reason>` in `reports/last-window/`.
- **Check:** `last-window trigger --dry-run --modes resume` prints every mode's gate, the burn-mode state and the sessions the limit stopped, and sends nothing.

## Optional team add-ons (not shipped in agent-crew-kit)

The installer keeps the opt-in flags `--slack-inbox` / `-SlackInbox` (token-free Slack inbox poller), `--slack-triage` / `-SlackTriage` (Slack/mail request triage into GitHub issues) and `--stale` (daily stale-branch cleanup). They run the team's own scripts from `tools/slack-triage/` in the clone, which this kit does not ship. Without that folder the installer stops the option with a clear message (`ERROR: ... not in this clone ...`) and changes nothing else. The status line's Slack segment stays silent when the poller is not installed.

## pace-peer sync is off

`pace-peer.json`, used when two machines share one account, is **not created** by this install; without the file the SSH sync between machines is skipped entirely. Do not create it on a single machine.
